# S3 Phase 1 — Scientific Report

## 1. Problem statement

S3 — Noise in Trotter Simulation is the selected problem statement for this repository.

## 2. Scope

Only the online Phase-1 A/B architecture study is treated as the common benchmark. Processor C and custom Processor D are excluded.

## 3. Compliance boundary

The supplied competition materials require the online phase to run the same selected problem with controlled settings on Processor A and Processor B and report solution quality, depth, two-qubit gates, SWAP/routing overhead, physical-qubit use and noise/reproducibility evidence. The Bell-correlation/protection challenge is reserved for the offline C/D stage.

The repository therefore keeps Bell-state/protection code only as auxiliary engineering material. It is not used as the Phase-1 S3 common benchmark.

## 4. Method

Problem/algorithm → logical Trotter circuit → processor-specific placement/routing → noisy execution model → problem/solution metric + architecture metrics → A/B comparison.

The runnable practice path uses a small first-order Trotter demonstrator with explicit illustrative parameters. It is a reproducible engineering scaffold, not an organizer-certified S3 instance.

## 5. Architecture experiment — practice models only

The same logical Trotter workload is compiled for two illustrative processor graphs:

- Processor A: fully connected five-qubit practice comparator.
- Processor B: five-qubit line practice comparator.

The line topology introduces routing operations for the non-local interaction. The resulting changes are measured in depth, two-qubit gate count, routing/SWAP overhead, physical qubits and noisy solution-quality metrics.

These processor models and noise rates are not official competition definitions.

## 6. Noise and measurement handling

The practice Trotter path uses stochastic Pauli errors after gates and applies the configured readout error to the reported single-qubit Z expectation. Online mean/variance accumulation provides a reproducible uncertainty estimate.

## 7. Results

The committed practice result tables and figures are regenerated by the run_practice.py and make_practice_figures.py scripts and are checked by CI for reproducibility.

## 8. Limitations

The supplied materials state that the selected problem's Challenge Kit determines problem-specific instances, required outputs and exact Processor A/B definitions. Those organizer-defined S3 inputs are not present in the current repository materials. All current Trotter settings, processor graphs and noise rates are therefore illustrative practice values.

## 9. Submission-readiness gate

The repository is engineering-green but competition-input-blocked. Official validation intentionally fails until the organizer-supplied S3 Challenge Kit is integrated, the official Processor A/B definitions replace the illustrative files, and the S3-specific outputs are regenerated.

## 10. Reproducibility

Random seeds, trajectory counts, processor JSON settings, generated tables and figures are versioned. CI rebuilds the notebook, executes the tests and regenerates the practice artifacts from source.
